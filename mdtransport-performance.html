Computational Performance of MDTransport for MD Trajectory Analysis

Related Pages: Course Home Molecular Dynamics Fundamentals Advanced Topics

Overview

This page presents a systematic analysis of the computational performance reported in the MDTransport paper (Verma, Thorat & Shah, J. Chem. Inf. Model. 2026, 66, 9989–10003). MDTransport is a Python tool for computing transport properties (ionic conductivity, diffusion coefficients, Onsager coefficients, etc.) from GROMACS and LAMMPS trajectories.

We extracted every numeric performance value from the paper, standardized the units, and compared them to understand what drives differences in postprocessing time and memory usage.

The paper benchmarks a 100 ns trajectory of a 500 ion-pair [C2mim][BF4] system for Einstein ionic conductivity calculation (20,001 frames at 5 ps interval). All values below are from Figure 3 and Figure 4 of the paper.

Why Do the Values Differ? — Factor Analysis

1. File Format: Binary ≫ Text (Dominant Factor)

Binary formats (.xtc, .trr) are processed ~10× faster (0.14 min) than text formats (.pdb at 1.52 min, .lammpstrj at 2.14 min). This is because binary formats avoid ASCII parsing overhead and are more compact on disk.

Paper quote: "It may be observed that, generally, analysis performed on the files in the pdb format is slower than that on the files in the xtc format." (Row 47, flagged — qualitative)

2. Parser Choice: Significant Interaction with Format

Different parsers excel for different formats:

  • Chemfiles: Fastest for .pdb (1.52 min) and binary (0.14 min); lowest memory for text formats (0.50 GB .pdb, 0.43 GB .lammpstrj)
  • OVITO: Most time-efficient for .lammpstrj (2.14 min)
  • MDAnalysis: Lowest peak memory for binary trajectories (0.55 GB); MDTransport's default backend

Paper quote: "the exact factor of improvement may vary based on the tools used, specifically across MDAnalysis, Chemfiles, or OVITO" (Row 48, flagged — qualitative)

3. Hardware Platform: Mac ≫ Intel/AMD

"calculations ran substantially faster on MACs as compared to Intel and AMD-based processors with --n_cores = 8 for a large file" (Row 50, flagged — qualitative). Figure 3(d) shows Mac Mini M2 Pro outperforming Intel Xeon Gold 6130.

The M2 Pro's unified memory architecture likely benefits memory-bound trajectory parsing, but the paper does not analyze this mechanism.

4. Core Count & Scaling: Sublinear, Format-Dependent

Performance improves with more cores but scaling is sublinear: "the improvement in processing speed with higher number of cores is also slightly correspondingly less when pdb file format is employed" (Row 48, flagged). The paper uses 1 and 8 cores in Figure 3(a) benchmarks but does not report explicit speedup ratios.

External literature (Khoshlessan et al. 2020, DOI:10.1002/cpe.5789) shows near-ideal strong scaling up to 384 cores with parallel HDF5, achieving ~100× speedup over serial (Row 53, flagged — "two orders of magnitude").

5. Memory Mode: Disk-Based Cuts Memory ~50%

"disk-backed storage option offloads extracted coordinate data to temporary disk storage rather than maintaining the entire data in RAM, reducing peak memory requirements by approximately 50% compared to standard in-memory processing (Figure 4(c,d))" (Row 45).

Trade-off: "increased I/O overhead may result in longer processing times for exceptionally large systems due to disk read latency" (paper, page 13).

What Remains Unexplained

  1. Absolute scaling factors: The paper reports wall times but not speedup ratios (1 core → 8 cores). Without baseline single-core times for each parser/format, parallel efficiency cannot be quantified from this paper alone.
  2. I/O vs compute breakdown: For disk-based mode, the paper notes I/O overhead but does not quantify the compute/I/O split.
  3. Generalizability to other properties: Benchmarks only cover Einstein ionic conductivity. Other properties (MSD, Onsager coefficients, cage lifetimes) may have different performance profiles.
  4. Comparison to other tools: The paper compares MDTransport's parser backends but not against standalone tools like PyLAT, TRAVIS, or STACIE. Table 2 shows feature comparison but not performance.
  5. Why Mac outperforms x86: The M2 Pro's unified memory architecture likely benefits memory-bound trajectory parsing, but this is not analyzed.
